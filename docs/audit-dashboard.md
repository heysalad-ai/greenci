# Audit and repair dashboard

`/app/audit` extends GreenCI's existing product shell with an organisation-scoped repository audit, searchable/filterable inventory, per-repository findings, and a repair queue with real draft PR links. Repair state, local verification and hosted PR checks are separate. A draft with passing local tests can still have failed, blocked or absent GitHub checks. The page shows dated saved observations and does not claim continuous monitoring.

Only local/dev API environments expose `GET /v1/audit`. Existing session validation and membership checks apply, followed by an owner-role check. Artifacts are loaded from private R2 keys `audit/<session-org>/current.json`, validated with Zod, tenant checked and served with `private, no-store`. Audit snapshot upload remains operator-only. Explicit owner-initiated repair requests use the separate guarded endpoints below. Public preview assets contain no private report data. The dev App's practice-only write scope stays unchanged.

To refresh dev observations, use the existing authenticated CLI with `pnpm audit:dashboard <private-audit-report.json> <private-repairs.json> <private-output.json> [org]`. It queries each draft PR, rejects moved heads or non-draft/closed PRs, and records actual check rollups. Failed job billing annotations are distinguished when available. Upload only the validated organisation dataset to the existing dev R2 bucket. Keep all inputs/outputs in ignored private storage.

`pnpm repair:publish <private-plan.json>` publishes a review branch from an exact, freshly checked parent commit. It validates source hashes before creating a commit, restricts changes to dependency manifests/locks plus explicit operator-approved, non-sensitive source/test paths, and refuses default-branch pushes through the core guard. `mode: update` accepts only a fast-forward update to the same repair branch. It never creates/approves/merges a PR, changes repo settings, installs an App or executes customer code. Draft PR creation remains an explicit authorised operator action through the GitHub connector. The local publisher remains available for operator-assisted repairs. The hosted dashboard can now launch the bounded source-repair profile described below; it is not an arbitrary-command or arbitrary-framework executor.

Tests use fake data and local Workers bindings: schema/PR URL validation, unsafe publish paths, anonymous/reader/other-tenant denial, private cache headers, search/filter/detail keyboard focus, mobile overflow and auth/error recovery. Real GitHub calls happen only during owner-authorised runtime operations, outside tests. No audit result or private repository data belongs in a commit.

## Hosted source-repair starts (dev)

The owner can select an eligible connected repository and press Start repair. `GET /v1/audit/options` rechecks installation allowlisting, write permission, a pinned default commit, a failing check and the supported dependency-free `test.mjs` profile. `POST /v1/audit/repairs` accepts only repository, exact SHA and a UUID idempotency key; it does not accept shell commands, model prompts or caller-defined policy. Owner/tenant, CSRF/origin, dev/OpenAI/Cloudflare-sandbox and body-size guards apply. The App installation and configured repository allowlist are unchanged; scanned repositories are not automatically repair-enabled.

Migration 0005 adds dashboard request records and an atomic unique active-org constraint. Duplicate keys recover the same run. One per-run durable Workflow automatically diagnoses, repairs and verifies, and opens a draft only after the existing code-based verification gates pass. Repo-level automation settings are untouched. Protected/high-risk changes pause for existing human review. Failures and out-of-scope results do not become verified, and terminal results release capacity. API probes and workflow creation can be retried against the same request; the UI offers recovery for an interrupted start.

`GET /v1/audit/repairs` reads authenticated run records every five seconds while the page is open. It is separate from historical audit snapshots. Once the start is accepted, execution does not rely on browser polling. Live run review/diff/approval and the resulting draft PR use existing screens. Automatic phase keys are disabled for these runs to avoid mixing one-click execution with manual phase events. No merge or PR-approval capability is added.

The current hosted profile supports source fixes using original dependency-free tests in an isolated no-internet container. Dependency updates, package installs, workflows and unsupported frameworks require another reviewed profile. Repository connection does not imply that arbitrary tests can be executed safely or that every audit finding can be repaired automatically.
